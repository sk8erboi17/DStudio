# Learn workspace, messages during generation and resume — November 10, 2026

This change preserves the earlier uncommitted Learn work of November 6 and 8.
It does not resume a user's generation or qualify P3/P6. One explicit
real-weight check used the already running DeepSeek V4.1 Flash engine with SSD
expert streaming; see *Verification*.

## Learn workspace redesign

The Learn screen follows the reviewed mockup (paused draft and generation in
progress). Everything shown is derived from the saved roadmap and audit ledger.

- **One status panel.** It replaces the stacked *paused* and *draft* notices of
  a stopped draft. It shows:
  - what exists: all stages written, or N/M stages;
  - the factual-check progress as a bar with a legend: confirmed, not factual,
    to verify, contradicted, and still to do;
  - one primary **Riprendi bozza** action, with a caption saying which saved
    checks are reused;
  - messages still waiting for an answer;
  - collapsed technical details, including the last step reached.
- **Header chips.** Completion, stages and blocks, required plus optional
  hours, and a status chip (*verified*, *modified · not verified*, *draft
  stopped* or *draft being written*). Drafts show their shape as well. Older
  roadmaps without a verification record make no claim.
- **Stage map.** When the card is at least 900 px wide, a sticky map sits
  beside the curriculum. Each stage shows its blocks, hours, which earlier
  stages it depends on, completion and a verification mini-bar, and the final
  project closes the list. Choosing an entry opens and reveals that stage. The
  entry for the stage being read is highlighted.
- **Collapsible stages.** On first view, the stage to continue and the next
  one are open and later stages are collapsed. While drafting, only the stage
  being written is open. Opening and closing is remembered for the view only.
- **Quiet block rows.** Each row shows its hours, short names of required
  blocks, its verification count, and an *Optional* tag only where it applies.
  The always-visible white *Study* buttons are gone: *Studia* and a **⋯** menu
  appear on pointer hover or keyboard focus, without moving anything. The menu
  holds *add a block after* and *delete*, away from the title. It supports
  arrow keys and Escape and announces its expanded state. The completion box is
  disabled with an explanation on unverified drafts.
- **Block details.** Summary, key-concept chips, three cards (expected
  outcome, practice, mastery check), sources, *Studia questo blocco*, a
  draft-tutor tag when unverified, and *add a block after*.
- **Checkpoints and final project.** A checkpoint shows its first clause, and
  its remaining clauses become expandable criteria, with no words added or
  lost. The final project lists deliverables and success criteria. When saved
  checks exist, it also shows its own verification count.
- **Generation in progress.** The progress panel names the current phase
  (*Sto scrivendo la tappa 3 di 6*, *Verifico i fatti · 40 di 122*) and shows
  a phase bar: research, structure, each stage, verification, judgement.
  - A callout announces the first readable draft and links to it.
  - The *Messages to the model* panel sits beside the draft, also before the
    first message.
  - Stop stays in the shared composer, so the progress panel has no second
    Stop button.
- **Learn opens at the top** of a roadmap and keeps its place on re-render,
  instead of following the last line like a chat transcript.
- Learn's visible labels, the add-block form and its progress messages are in
  Italian, matching the content. Shared composer controls are unchanged.
- **Export** renders every stage expanded, without the map or menus.
- Legacy roadmap-card and status CSS (about 250 rules from three generations)
  was removed and replaced by one block of theme-token rules for light and
  dark mode.

## Messages while a roadmap is generated

- The Learn prompt stays usable during generation, and its placeholder says
  that the text goes to the running model. A message is saved durably before
  it is acknowledged. It is a note on the current roadmap request, not a new
  request.
  - Previously, generic steering aborted the running step and rebuilt the
    roadmap from the new message as a new request. The new request had no
    reusable draft, so the work already authored was not reused.
  - Now the running step is never aborted. At the next phase boundary (before
    the next stage, audit batch, repair or final check), the model receives the
    pending messages with the current draft and answers each one.
  - Stages written after the answer carry the message and the answer as
    learner guidance.
  - When the model decides that already written stages must change, the change
    is applied where the whole draft is consistent: after the last stage, or
    at an audit boundary.
  - A targeted rewrite replaces only the named stages. It keeps every agreed
    topic in order, with its id, prerequisites and required/optional status.
    It may add up to four new topics inside a rewritten stage, with new ids and
    prerequisites only on earlier topics, and the saved outline records them.
  - A structural change (stages added, removed or reordered, or topics moved
    between stages) uses the existing preserve-ids repair path, which
    regenerates every stage.
  - After a rewrite the audit resumes. Saved receipts for unchanged items are
    reused, and the changed content is checked again before success is shown.
  - Only text is accepted during generation. Attachments are refused with an
    explanation and stay in the composer.
- Messages written while an accepted roadmap is being updated appear with the
  update notice.
- A message that arrives after the final boundary of a verified run is marked
  as not delivered, so it does not stay silently pending.
- Toasts report the first readable draft and the completed draft. Opened
  blocks stay open while the draft re-renders.

## Ownership and bounds

- Notes live in `chat.roadmapNotes`, keyed by the roadmap request's user
  message. The chat store remains their only authoritative copy; the runner
  updates their state and the view renders them.
- The chat keeps at most 72 notes for other existing requests, plus 24 for the
  current request.
- Notes are not part of the draft input key. A draft written before or after a
  message stays resumable. Pending messages are answered when the draft is
  resumed. An agreed but unapplied rewrite is applied after resumption.
- Limits per request:
  - each learner message is at most 4,000 characters;
  - at most 8 messages can be pending, and at most 24 can be kept;
  - each answer and each revision description is at most 2,400 characters.
    Overlong replies are refused for bounded recovery; they are never cut.
- At most 8 consecutive feedback rewrite rounds run before the attempt stops
  as incomplete. The draft and the messages are retained.
- A targeted rewrite cannot drop, rename, reorder or re-link agreed topics. It
  adds at most four topics per stage, and their ids may not be used elsewhere.
  Unwritten stages cannot be targeted. Before an outline exists, a reply must
  not request a rewrite; the message guides the outline instead.
- Learner text reaches the model as JSON data inside the phase request. It is
  explicitly learner content, never protocol instructions.
- If the model fails to answer, the message is marked failed. Its text remains
  guidance for later stages, and generation continues. Stop still aborts any
  phase, including a note reply.
- View state is not authoritative and is not persisted: open stages, open
  blocks and the highlighted map entry are bounded to the last 8 roadmaps. Only
  one stage observer exists at a time.

## Verification

### Model-free and simulated-engine checks

- **Unit tests.** `make test-roadmap-request` now adds
  `tests/unit/roadmap_notes_test.mjs` (reply admission, the JSON-bounded
  request, lazy guidance, targeted rewrites, partial previews, resumability)
  and `tests/unit/roadmap_view_test.mjs` (audit counts, hours, dependencies,
  short titles, lossless checkpoint criteria). Both pass, as does
  `tests/unit/frontend_behavior_test.mjs`.
- **Simulated UI matrix** (`make test-ui-simulated`, 28 suites plus three Qwen
  Learn variants, in WebKit and Chromium): every Learn, Chat, Agent, Cowork,
  sidebar, model, loading, settings and workflow suite passes, with three
  exceptions:
  - `ui_model_picker_playwright_test` already failed at `HEAD` in both
    browsers. Since November 5 the app requires a durable acknowledgement of
    history writes, and the test's own host mock never sent one, so a
    persistence warning covered the composer. That mock now mirrors the
    host's `{"ok":true,"durable":true,"rev":N}` reply, as does the shared
    `tests/support/ui_mock_server.mjs`. The suite passes in both browsers.
  - `ui_agent_design_playwright_test` fails in WebKit with "the first Design
    prompt must not race a fresh-session context prefill". It fails the same
    way on an archive of `HEAD` (3 of 3 runs), so it is a pre-existing Design
    issue outside this change and is not fixed here.
  - Under heavy load (the real-weight run below in parallel), WebKit
    occasionally failed timing assertions in three Learn scenarios. All three
    passed twice when idle. One of them waited a fixed second for an
    asynchronous save; it now waits for the saved record.
- **Learn scenarios.** Normal, notes, partial audit, audit recovery, missing
  evidence, recovery (including the legacy draft) and storage failure pass in
  Chromium and WebKit on the final code. So do `make test-ui-persistence`,
  `make test-ui-native-titlebar` and the hover/keyboard controls test (light
  and dark, 1100 and 760 px).
  - The hover test's GIF encoder needs Pillow, which the default `python3`
    lacks. The runs used another local Python that has it.
- **Build.** `make -j2 all` builds the signed app.
  `scripts/smoke-macos-bundle.sh DStudio.app` passes on an idle machine. While
  the engine and browsers were running, it failed once because its fixed
  5-second start window elapsed; a manual start took 7.1 s.
- **Install.** The final build is installed in `~/Applications` and
  relaunched. The served page matches `web/index.html`, and the engine
  restarted from its saved settings with effective SSD streaming. The user's
  saved Learn draft is unchanged: six stages and 103 of 122 checks.
- **After the targeted-rewrite fix**, the following were rerun on the final
  code, and all pass:
  - every Learn scenario in Chromium and WebKit, including the notes scenario
    and all three Qwen variants;
  - the hover/keyboard test;
  - the unit tests;
  - the clean build and the smoke test.

### Real weights

`make test-real-roadmap-notes` (`tests/live/real_roadmap_notes_test.mjs`) ran
against the installed app's engine with `DSTUDIO_LIVE_HOST`. That engine is
DeepSeek V4.1 Flash 1017 IQ2_XXS at 131,072 context with high reasoning, and
`ssdStreamingEffective` reported true. It decoded at about 7 tokens/s. Every
receipt is kept under ignored `tests/.artifacts/roadmap-notes-real/`.

- **Run 1: failed.** The JSON reply was valid and the answers were correct
  Italian (exposure determines the data that post-production can work with).
  For "add a night exercise with a tripod" the model chose `structure`
  (adding a topic) rather than `stages`. The protocol defines added topics as
  structural, so the grader's single expected value was the defect. The
  grader now accepts either decision, keeps the requirement that the change
  lands in the composition stage, and executes the chosen production path. A
  separate unambiguous in-place case (B) now exercises the targeted rewrite.
- **Run 2: failed.** The model again chose `structure`. The production
  preserve-ids repair ran outline plus three stages in about 37 minutes. It
  kept every agreed id and added a `fotografia-notturna` topic with a
  night/tripod practice to `composizione`. The production quality gate then
  refused the result: the authored fixture had one source URL, and real
  roadmaps need at least three. The fixture now has three, and its draft must
  pass the quality report before any model call.
- **Run 3 (product defect found):** the model chose `stages` for the
  composition stage. Its rewrite kept both agreed topics and added a valid
  `notturna-cavalletto` topic. The production stage normalizer accepted only
  the agreed topic ids, so it refused the rewrite. In the app, that refusal
  would have stopped generation after three attempts and recurred on every
  resume.
  - Fix: targeted rewrites now admit new topics inside the rewritten stage,
    with the bounds above, and the outline is updated.
  - `tests/unit/roadmap_notes_test.mjs` covers the accepted addition, the
    saved grown outline and resume validity. It also covers rejection of
    duplicate ids, later prerequisites, changed agreed edges, dropped or
    reordered agreed topics, too many additions and a wrong stage id.
  - The live grader now requires the agreed topics in order, rather than
    exactly the agreed ids.
- **Run 4: passed, with no automatic retries.** Elapsed times include a
  shared host and parallel browser tests; they are not benchmarks.
  - Case A: the model answered both messages and chose `stages` for
    `composizione`. The targeted rewrite kept both agreed topics and added
    `fotografia-notturna`, with every other stage unchanged. The notes phase
    took 380 s and 1,623 completion tokens; the rewrite took 1,127 s and 5,852
    tokens.
  - Case B: `stages` for `composizione`. The model rewrote only the practice
    of `luce-naturale` and added no topic. The notes phase took 217 s; the
    rewrite took 477 s and 2,132 tokens.

Observed cost: the structural path regenerates every stage. In run 2 that took
about 37 minutes for three stages. Run 3 showed that the model can satisfy
"add an exercise" inside one stage; with the fix above, that no longer forces
a full regeneration.
